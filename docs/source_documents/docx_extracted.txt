BCA MINI PROJECT
Foundation Integration Course
Four Themes  ·  Project Titles  ·  Worked Examples  ·  Gate Assessment Sheets
Department of BCA  ·  KLE Technological University, Belagavi
Mini Project — Foundation Integration Course: the S0 to S7 stage model, the Gate 0 to Gate 4 structure carrying 50 marks, the Basic / Apply / Analyze / Decision question ladder, and the engine-based decomposition. 
A BCA teams build three engines, and integrates five foundational course areas.
How to use this handbook. Students read Part A and the theme they register under. Faculty mentors read Part A and Part C. Each team needs five assessment sheets — the five gate sheets for their own theme, printed from Part C. Both the student and the mentor fill the same sheet, in their own columns, independently.
PART A — The Framework
Course Outcomes
Every assessment row in Part C carries the course outcome it evidences. This is what makes attainment measurable rather than asserted.
CO
On successful completion, the student will be able to…
CO1
Analyse the problem, its scope, the foundational concepts it needs, and the objectives
CO2
Formulate a structured requirements specification with FRs, NFRs, constraints and workflows
CO3
Design a modular architecture: engines, data model, data structures, algorithms, interfaces
CO4
Develop an integrated solution using programming, data management and web principles
CO5
Evaluate through failure-mode testing, validation, debugging, refinement and a technical report

Worked example — Exam Hall Ticket Issue Register
The problem: Hall tickets are withheld at the counter on the morning of the examination because a due or a shortage was discovered late. The student cannot fix it in time and loses the paper.
The one rule: A hall ticket is issued only if attendance is 75% or more in every registered subject, there are no fee dues, no library dues, and no disciplinary hold. A single failing condition blocks issue, and the reason must be shown.
The three engines
Engine
Course area
What it does
Engine 1 — Student & Clearance Data Engine
DBMS
Tables for student, subject registration, attendance, dues and holds. Constraints so a clearance cannot point at a non-existent student. Transactions when a due is cleared.
Engine 2 — Eligibility Rule Engine
Data Structures + Programming
Evaluates all four conditions, returns issue or block plus every failing reason. Rule parameters read from a table with a validity period, not hard-coded.
Engine 3 — Issue & Verification Interface
Web Technologies
Role-based screens for student, clerk and controller. Server-side re-validation so a direct request cannot bypass the check. Hall ticket generation with a verification code.

Worked example — Library Catalogue Ranked Search
The problem: Students search the catalogue by exact title. A near-miss spelling returns nothing, and when many copies match, the order is whatever the database returned, so a reference-only copy often appears above a lendable one.
The one rule: Results are ordered by a relevance score the team designs — title match weight, availability, edition recency and copy count — and the same query must be shown under two different orderings and compared.
The three engines
Engine
Course area
What it does
Engine 1 — Catalogue & Index Engine
DBMS
Schema for title, author, subject, edition, copy and availability. Index designed on the searched columns, with query time measured before and after.
Engine 2 — Retrieval & Ranking Engine
Data Structures + Programming
Inverted index or hash map built from scratch over title and subject tokens. Scoring formula, sorting, tie-breaking, complexity note.
Engine 3 — Search Interface Engine
Web Technologies
Asynchronous query, result rendering, and designed behaviour for the empty result and the thousand-result cases.

Worked example — Lab Equipment Issue and Return Ledger
The problem: Components are issued to students for project work against a register. At the end of the year nobody can say who holds what, and the physical count never matches the register.
The one rule: Stock can never fall below zero. Issue, return and receipt are all transactions. The balance is the sum of receipts minus issues plus returns, computed at the moment it is displayed — it is never stored as a number.
The three engines
Engine
Course area
What it does
Engine 1 — Transaction & Integrity Engine
DBMS
Item master, transaction table, user table and audit table. Foreign keys, a CHECK preventing negative issue, and an explicit transaction so a two-part posting cannot half-complete.
Engine 2 — Balance & Custody Engine
Data Structures + Programming
Derives the balance by aggregation. A queue structure gives oldest-first consumption and the outstanding-custody list per student. Complexity note on the aggregation.
Engine 3 — Issue Counter & Audit Interface
Web Technologies
Issue, return and audit screens with roles. Server-side re-check on every posting, so two simultaneous requests cannot both succeed against the last unit.

Worked example — Attendance Shortage Report System
The problem: Shortage lists are produced late, disputed by students, and computed differently by different staff. Three people produce three percentages from the same register.
The one rule: Attendance percentage is attended classes over conducted classes — but cancelled classes, extra classes, students who joined mid-semester, and subject-wise versus aggregate attendance each give a different and defensible answer. The team must define the calculation, document what it excludes, and defend it.
The three engines
Engine
Course area
What it does
Engine 1 — Data Intake & Cleaning Engine
DBMS
Reads the attendance register, records what arrived — row count, columns, malformed rows — and applies each cleaning rule with the number of rows it affected.
Engine 2 — Aggregation & Verification Engine
Data Structures + Programming
Computes each report as a documented query, never a stored table. Recomputes every headline number by a second independent method and compares.
Engine 3 — Report & Notice Interface
Web Technologies
Subject-wise and aggregate views by role, with every displayed number linked to the query that produced it, and shortage notices generated per student.
